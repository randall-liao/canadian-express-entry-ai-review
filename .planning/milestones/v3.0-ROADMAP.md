## Active Milestone

### v3.0 — Grounded Answer Layer

**Goal:** Bring the answer half into the shareable repo — FTS5 retrieval + a fail-closed grounding
gate + the personalized Layer-1 document checklist + portable document agents — producing cited,
grounded answers about which PR documents the applicant needs, with PII kept strictly local.

**Acceptance bar (locked):** *grounding-by-construction* — every factual claim in a generated
answer/checklist must carry a citation that resolves to a real corpus chunk **and** whose verbatim
quote exists in that chunk; any uncited or unresolvable claim fails the entire output (fail-closed).
The gate that enforces this doubles as the automated eval harness.

**Build order (gate-first, research-converged):** retrieval lands first (an FTS5 index, then a
`search` verb + citation resolver), then the grounding gate (the contract every later producer emits
into), then the producers — the personalized checklist and the document agents. Every v3.0
requirement maps to exactly one phase.

#### Phase 23: FTS5 Index Builder

**Goal**: A re-runnable SQLite FTS5 keyword index exists over the clean 742-doc corpus, with every chunk carrying resolvable citation metadata — the citable ground every later answer stands on.
**Depends on**: Nothing new (builds on the shipped corpus + `crawler/` primitives: `dupaudit.live_docs`/`body_of`/`_frontmatter_of`, `profile._HEADING_RE`, `contract` envelope). First v3.0 phase.
**Requirements**: RET-01
**Success Criteria** (what must be TRUE):

  1. Running `corpus-crawler --json index corpus/ --db corpus/index.db` builds an FTS5 index over exactly the live-doc set (reusing `dupaudit.live_docs`, the 742-filter), and re-running it produces byte-identical `chunk_id`s — idempotent, diffable rebuild. [RET-01]
  2. Every chunk row carries its five citation fields — corpus-relative path, source URL, title, section (heading breadcrumb + statutory marker for legislation), crawl date — derived from front-matter + ATX headings, never invented; the stable `chunk_id` is `relpath#ordinal` (content coordinates, not the DB rowid). [RET-01]
  3. The chunker bounds chunk size deterministically: tiny docs become one whole-doc chunk; the ~0.5–1 MB IRPA/IRPR `FullText` docs split on headings into bounded chunks with no unbounded chunk. [RET-01]
  4. The index DB lives under git-ignored `corpus/` and contains corpus text + citation metadata only — no PII, no vectors/embeddings, and no new runtime dependency (stdlib `sqlite3` FTS5); if the host SQLite lacks FTS5 the builder fails loud with an actionable error + non-zero exit. [RET-01]

**Plans**: 3 plans (waves 1→2→3; one cohesive `searchindex.py` module built incrementally)

- [ ] 23-01-PLAN.md — `searchindex.py` foundation: scaffold + FTS5/`chunks` DDL constants + fail-loud FTS5 probe + deterministic heading-aware chunker [SC2/SC3/SC4]
- [ ] 23-02-PLAN.md — `build_index`: live-doc loop (`dupaudit.live_docs`), five citation fields + stable `chunk_id = relpath#ordinal` + `chunk_sha`, idempotent rebuild [SC1/SC2]
- [ ] 23-03-PLAN.md — `index` CLI verb (thin dispatcher + FTS5 fail-loud) + additive CONTRACT.md/contract.py docs + JSON-envelope & real-corpus 742 smoke tests [SC1/SC4]

#### Phase 24: `search` Verb + Citation Resolver

**Goal**: Any CLI-agnostic agent can search the corpus for ranked, citable chunks and resolve a citation back to its exact chunk — all through the existing `crawler/CONTRACT.md` JSON-envelope contract.
**Depends on**: Phase 23
**Requirements**: RET-02
**Success Criteria** (what must be TRUE):

  1. Running `corpus-crawler --json search "<query>"` returns BM25-ranked hits, each with a stable resolvable citation ID (`relpath#ordinal`), full citation metadata, and a highlighted `snippet`, emitted as exactly one CONTRACT.md envelope on stdout (human text on stderr). [RET-02]
  2. A citation ID resolves back to its exact chunk via a `--cite <id>` resolver; an unknown or stale (content-drifted) ID returns "not found" / fail-closed — this is the resolver the grounding gate (GND-01) calls. [RET-02]
  3. Adversarial queries are safe: section codes like `R30(3)`, apostrophes, and bare `OR`/`AND`/`NEAR` are treated as literal terms (no FTS5 syntax error, no injection, no silent column-filter); an empty / all-punctuation query returns `INVALID_INPUT` instead of running an empty `MATCH`. [RET-02]
  4. Adding `index`/`search` is additive — the five envelope keys and `schema_version "1.0"` are unchanged, and `CONTRACT.md` + the `contract.py` command list document both new result shapes 1:1 with the code, so existing crawler consumers are unaffected. [RET-02]

**Plans**: 3 plans (waves 1→2→3; read-only over the Phase-23 index — all share `searchindex.py`/`test_searchindex.py`, so sequential)

- [x] 24-01-PLAN.md — `_to_match()` adversarial-query escaper + read-only `search()` BM25 query (snippet, stable chunk_id) [SC1/SC3]
- [x] 24-02-PLAN.md — `resolve()` citation primitive: exact verbatim chunk, fail-closed on unknown/sha-drift (the GND-01 resolver) [SC2]
- [x] 24-03-PLAN.md — `search` CLI verb + `--cite` mode + additive CONTRACT.md/contract.py docs + CLI-envelope & real-corpus round-trip tests [SC1/SC2/SC3/SC4]

#### Phase 25: Grounding Gate + Eval Harness

**Goal**: A fail-closed grounding-by-construction gate turns structured agent answers into trustworthy cited output, and the same gate run over a tracked PII-free question set IS the automated eval harness. This is the contract every later producer (checklist, agents) emits into.
**Depends on**: Phase 24 (the `--cite` citation resolver)
**Requirements**: GND-01, GND-02
**Success Criteria** (what must be TRUE):

  1. Answers are one structured JSON object — `{question, claims:[{id, text, citations[], quote}], basis[], abstentions[], prose}` — and the gate (`corpus-crawler --json ground`, reading stdin) checks **only** `claims[]`; `prose`/`basis`/`abstentions` are never citation-checked, so non-factual filler never triggers a false failure. [GND-02]
  2. **Grounding-by-construction, fail-closed:** every claim must carry ≥1 citation that resolves to a real chunk (GND-01) **and** whose verbatim `quote` is a whitespace/case-normalized substring of that chunk; ANY uncited, unresolvable, or quote-mismatch claim makes the gate emit `verdict:"fail"`, render nothing user-facing, and exit non-zero. [GND-01, GND-02]
  3. A passing answer renders only to the git-ignored `personal/output/` area and is re-scanned with `check_publish_safe.scan_text` (RPT-03 render-then-gate) before write — a PII / secret / abs-path hit refuses the output with `ok:false` and exit 4. [GND-02]
  4. The same gate run over a tracked, PII-free `questions.jsonl` reference set (including adversarial `must_abstain` questions) emits `eval_runner`-style `{total, passed, failed, failures}` and exits non-zero if any answer is ungrounded — the gate doubles as the eval harness, with uncited-claim count / citation-resolution rate / quote-substring rate / abstention-correctness as hard 0%/100% gates. [GND-02]
  5. The gate's honesty boundary is explicit and documented: it guarantees resolvability + verbatim-quote, **not** semantic entailment/faithfulness (true entailment needs a model/NLI and is deferred with VAL-01/02); quote and claim render side-by-side for human review. [GND-02]

**Plans**: 3 plans (sequential waves — shared files force strict ordering)

- [x] 25-01-PLAN.md — Pure-stdlib grounding compute module `crawler/grounding.py` (per-claim resolve + verbatim-quote fail-closed verdict + render) + unit suite [GND-01, GND-02]
- [x] 25-02-PLAN.md — `ground` CLI verb (stdin → envelope; verdict-fail exit 1; render-then-scan to `personal/output/`; publish-unsafe exit 4) + additive CONTRACT.md/contract.py docs [GND-01, GND-02]
- [x] 25-03-PLAN.md — Eval harness (`--eval` over a tracked PII-free `crawler/eval/questions.jsonl`; `{total,passed,failed,failures}`; adversarial `must_abstain`) [GND-02]

#### Phase 26: Personalized Layer-1 Checklist + PII Separation

**Goal**: Generate a personalized, fully-cited Layer-1 "which documents you need" checklist for a post-ITA Express Entry applicant from a LOCAL profile, with all PII kept strictly out of the repo and the corpus DB.
**Depends on**: Phase 25 (every checklist requirement line passes through the gate)
**Requirements**: CHK-01, CHK-02
**Success Criteria** (what must be TRUE):

  1. Running the checklist generator against `$PR_PERSONAL_DIR/profile.yaml` (default `./personal/`) produces a Layer-1 document checklist where every requirement line is a gated, cited `claims[]` entry that passes the Phase-25 gate. [CHK-01]
  2. Separation of concerns holds: profile-derived **applicability** (which items apply — e.g. countries lived in since 18) lives in `basis[]` / local files and is never citation-checked, while the **requirement text + citation** comes from the corpus and is gated. [CHK-01, CHK-02]
  3. The rendered checklist is written only under git-ignored `personal/output/`, and the publish-safety scanner's `CORPORA_PREFIXES` guard (already includes `personal/`) fails closed if any profile/output file is ever `git add`-ed; `personal.example/` (synthetic schema) stays tracked. [CHK-02]
  4. No PII (countries, dates, names) ever appears in `claims[].text`, the corpus DB, or any tracked file — confirmed by the RPT-03 publish-safe scan over the rendered checklist bytes. [CHK-02]

**Plans**: 3 plans (3 sequential waves)

- [x] 26-01-PLAN.md — Synthetic profile fixture + checklist module (loader, $PR_PERSONAL_DIR, applicable_items)
- [x] 26-02-PLAN.md — Checklist assembler: grounded PII-free claims[] + build_answer through the Phase-25 gate
- [x] 26-03-PLAN.md — `checklist` CLI verb (render→scan→write) + additive contract docs + real-corpus/PII self-scan tests

#### Phase 27: CLI-Agnostic Document Agents

**Goal**: Six portable markdown document-agent skills (police certificate, language test, ECA, proof of funds, medical, employment reference letter) answer document questions by consuming the `search` contract and emitting only gated, cited claims — identically across CLIs.
**Depends on**: Phase 25 (gate) and Phase 24 (`search`); reuses the local profile-slice pattern from Phase 26
**Requirements**: CHK-03
**Success Criteria** (what must be TRUE):

  1. Each of the six document agents is a thin plain-Markdown skill sharing one `_contract.md` (no proprietary front-matter) that retrieves via `corpus-crawler --json search`, copies a verbatim `quote` per claim from the retrieved chunk, and pipes its structured answer to `corpus-crawler --json ground`. [CHK-03]
  2. An agent emits ONLY cited claims; when the corpus has no answer it emits zero claims with an explicit `abstention` ("not in corpus") rather than confabulating, and the gate refuses any ungrounded output. [CHK-03]
  3. Per-CLI conformance: the same question run under Antigravity / Codex / Claude / Copilot passes the gate with the same resolved citation set — no CLI-native tooling sits in the trust path (all logic is in the Python gate + shell `search`). [CHK-03]
  4. The employment reference letter agent verifies an Express Entry employment/reference letter's required elements (e.g. company letterhead/contact, signatory + title, job title(s), dates/period of employment, hours/full-time status, annual salary + benefits, detailed duties) — each requirement statement gated + cited to the corpus, never hardcoded; no PII (employer name, dates, salary) in `claims[].text`. [CHK-03]
