## Active Milestone

**v4.0 — CRS Profile ↔ Document Substantiation Auditor**

**Goal:** Prove the applicant's claimed CRS score is substantiated by the documents they will actually submit — catching profile↔document mismatches before e-APR submission, with every admissibility/threshold verdict grounded and cited from the authoritative corpus.

**Granularity:** fine  
**Phase range:** 29–34 (continues after v3.1 Phase 28)  
**Requirement coverage:** 24/24 v4.0 requirements mapped  
**Core build order:** vault privacy perimeter → extraction quarantine → grounded rule registry → auditor slice → full auditor pack → safety/release hardening.

**Locked constraints for every phase:**

- All PII stays in the git-ignored candidate vault; never in the repo, corpus, stdout, public reports, tracked fixtures, or `.planning/`.
- Extraction is the only non-grounded step and remains `pending` until field-level user confirmation.
- Every admissibility/threshold verdict is fail-closed and grounded through the frozen v3.x `search` → `--cite` → grounding gate → JSON envelope primitives.
- Auditors are deterministic joins over confirmed evidence plus grounded CRS rule rows; no new trust-path code.
- Retrieval remains SQLite FTS5 keyword retrieval only; no vectors, embeddings, cloud OCR/document AI, or cloud APIs.
- Python remains Poetry-managed.

## Phase Details

### Phase 29: Candidate Vault & PII Perimeter

**Goal**: Applicant can safely store their CRS profile, ITA round/cutoff, and raw documents in a private vault that cannot contaminate the public repo or authoritative corpus.
**Depends on**: Nothing within v4.0 (builds on shipped v3.x search/`--cite`/ground primitives)
**Requirements**: VAULT-01, VAULT-02, VAULT-03, VAULT-04
**Success Criteria** (what must be TRUE):

  1. Applicant can create or select a non-PII candidate vault and store CRS factor breakdown plus ITA round/cutoff under the git-ignored personal boundary.
  2. Applicant can import raw PDFs/images and receive vault-local document/evidence IDs while files are content-addressed and kept out of the repo, corpus, and public reports.
  3. Candidate evidence is visibly separate from authoritative citations: `evidence_id` is never interchangeable with `citation_id`, and candidate text is never citable as authority.
  4. Attempts to stage or write vault DB/WAL files, rendered images, OCR text, logs, or private reports outside the vault are blocked by publish-safe/gitleaks/path-guard checks.

**Plans**: 4 plans

- [x] 29-01-PLAN.md — Dependency supply-chain gate + shared personal-path resolver (wave 1)
- [x] 29-02-PLAN.md — Candidate vault store: schema/models, profile/ITA, content-addressed evidence (wave 2)
- [x] 29-03-PLAN.md — Vault CLI verbs (init/profile/ita/import/list) + PII-light envelope (wave 3)
- [x] 29-04-PLAN.md — Publish-safe/gitleaks/path-guard hardening + PII-perimeter conformance (wave 3)

### Phase 30: Extraction Quarantine & Field Confirmation

**Goal**: Applicant can turn vault documents into field-level confirmed evidence while all automated extraction remains quarantined until reviewed.
**Depends on**: Phase 29
**Requirements**: EXTRACT-01, EXTRACT-02, EXTRACT-03, EXTRACT-04, EXTRACT-05
**Success Criteria** (what must be TRUE):

  1. Running extraction renders/reads vault documents and proposes structured fields such as test scores, dates, credentials, NOC/TEER, hours, duration, and issuer only as `pending` vault values.
  2. Applicant can confirm, correct, or reject each extracted field while seeing the raw value, normalized value, source page/crop, affected CRS factor, and profile claim.
  3. Pending, rejected, low-quality, or ambiguous extracted fields cannot become audit-eligible evidence and cannot support a green verdict.
  4. Replacing the source file, changing parser version, editing the profile claim, or updating the rule-registry version marks affected confirmations stale until re-confirmed.
  5. A doctor/preflight check reports missing extraction dependencies and scan-quality issues such as scanned, rotated, password-protected, or low-text documents instead of failing silently.

**Plans**: 4 plans

- [x] 30-01-PLAN.md — Extraction schema v2 + trust logic (pending-quarantine gate SC3, staleness SC4) (wave 1)
- [x] 30-02-PLAN.md — Extraction deps + engine: render/text/OCR, field extractors, scan-quality (wave 2)
- [x] 30-03-PLAN.md — Confirmation workflow: vault extract/fields/confirm verbs + eligibility/staleness surfacing (wave 3)
- [x] 30-04-PLAN.md — doctor/preflight + PII-perimeter hardening + SC1–SC5 conformance + CONTRACT docs (wave 4)
- [x] 30-05-PLAN.md — GAP-CLOSURE: extraction→auditor INTEGRATION seam (BLOCKER A per-document factor linkage + `--factor`; BLOCKER B shared test_type vocab + anti-drift gate; passport→core.age DOB; real extract→confirm→audit E2E regression) (wave 5)

**UI hint**: yes

### Phase 31: Grounded CRS Rule Registry & Deterministic Logic

**Goal**: Auditors have a PII-free, corpus-grounded CRS rule registry and deterministic CRS logic before any factor verdicts are implemented.
**Depends on**: Phase 30
**Requirements**: RULE-01, RULE-02, RULE-03, RULE-04, RULE-05
**Success Criteria** (what must be TRUE):

  1. For every CRS factor group, registry rows capture accepted proof types, validity windows, issuers, thresholds, caps, and admissibility predicates with resolving corpus citations and verbatim quotes.
  2. Every registry rule validates through the existing `search`/`--cite`/grounding gate, and static checks reject volatile CRS thresholds hard-coded in auditor prose.
  3. A coverage report shows the full CRS grid across core human capital, spouse/common-law, skill transferability, and additional points with no missing required rule rows.
  4. Deterministic Python logic computes CLB/NCLC conversion, date math, duration aggregation, spouse mode, transferability caps, and cutoff comparison from grounded rule rows.
  5. A non-zero arranged-employment additional-CRS claim is treated as `AT-RISK`/0 unless ITA-era corpus rules ground a legacy or exception case.

**Plans**: 5 plans in 3 waves (parallel-optimized; fine granularity)

Plans:

- [x] 31-02-PLAN.md — [wave 2] Grounded core-human-capital + spouse/common-law registry rows (CLB/NCLC conversion, validity windows, accepted tests, work defs) [RULE-01/03]
- [x] 31-03-PLAN.md — [wave 2] Grounded skill-transferability (caps 50/50/100) + additional-points rows incl. arranged-employment repeal [RULE-01/03/05]
- [x] 31-04-PLAN.md — [wave 3] Deterministic CRS logic (CLB conversion, date math, duration, spouse mode, caps, cutoff) + arranged-employment guard [RULE-02/04/05]
- [x] 31-05-PLAN.md — [wave 3] Full-registry conformance + public coverage report (COVERAGE.md) + aggregate no-inlined-volatile-rule check [RULE-02/03]

### Phase 32: Auditor Vertical Slice & Private Report Contract

**Goal**: Applicant can run one complete CRS auditor slice from confirmed evidence plus grounded rules and receive fail-closed, vault-only evidence-bearing output.
**Depends on**: Phase 31
**Requirements**: AUDIT-02, AUDIT-06
**Success Criteria** (what must be TRUE):

  1. A pilot factor slice emits `SUBSTANTIATED`, `GAP`, `AT-RISK`, or `N/A` only after every rule claim passes the existing grounding gate.
  2. `SUBSTANTIATED` is impossible unless required proof exists, evidence is confirmed/corrected, values meet the claimed threshold, and the admissibility/threshold rule is grounded and cited.
  3. Pending, low-confidence, stale, missing, or semantically unresolved evidence produces `GAP` or `AT-RISK`, never a green verdict.
  4. Public JSON/stdout remains PII-light with generic claims, counts, private output path, and run ID; full evidence-bearing reports are written only under the candidate vault.
  5. A grounding failure writes no partial report, while grounded `GAP`/`AT-RISK` findings are treated as valid audit results rather than execution errors.

**Plans**: 5 plans in 4 waves (fine granularity; pilot factor = first official language) — **COMPLETE**

- [x] 32-01-PLAN.md — Audit contracts: Verdict vocabulary + PII-light public / PII-bearing private report models (Wave 1)
- [x] 32-02-PLAN.md — Vault schema v3: audit_runs + factor_verdicts tables + record/load helpers (Wave 1)
- [x] 32-03-PLAN.md — Fail-closed first-official-language verdict engine (grounding gate → verdict matrix) (Wave 2)
- [x] 32-04-PLAN.md — Vault-only report writer + fail-closed persistence (no partial report on gate failure) (Wave 3)
- [x] 32-05-PLAN.md — `vault audit` CLI verb + PII-light envelope + publish-safe/PII perimeter (Wave 4)

### Phase 33: Full Modular CRS Auditor Pack

**Goal**: Applicant can audit every claimed CRS factor through four context-light modules and see substantiated points plus ITA cutoff risk.
**Depends on**: Phase 32
**Requirements**: AUDIT-01, AUDIT-03, AUDIT-04, AUDIT-05
**Success Criteria** (what must be TRUE):

  1. Every claimed or applicable CRS factor returns exactly one `SUBSTANTIATED`, `GAP`, `AT-RISK`, or `N/A` verdict with a grounded rule citation and private evidence pointer.
  2. Core human capital, spouse/common-law, skill transferability, and additional-points auditors run as separate context-light modules through the frozen v3.x primitives with no new trust path.
  3. Applicant can inspect factor cards showing claimed value, confirmed extracted value, substantiated points, score delta, evidence pointer, and rule citation.
  4. The audit compares the substantiated CRS total against the ITA round cutoff and surfaces score-impact risk without giving legal advice.
  5. Multi-document aggregation, spouse/principal ownership, work-interval conflicts, and transferability dependencies surface as factor-level `GAP` or `AT-RISK` findings rather than hidden document-level passes.

**Plans**: 7 plans
Plans:

- [x] 33-02-PLAN.md — Complete grounded CLB/NCLC conversion tables (all 5 tests × 4 abilities); makes language SUBSTANTIATED reachable
- [x] 33-03-PLAN.md — Spouse/common-law module (spouse-mode gating, N/A, ownership separation)
- [x] 33-04-PLAN.md — Skill-transferability module (5 combinations consume core cards; caps 50/50/100)
- [x] 33-05-PLAN.md — Additional-points module (nomination, arranged-employment guard, study, French, sibling)

### Phase 34: Safety Conformance & Release Framing

**Goal**: Release only when automated conformance proves fail-closed behavior, privacy containment, intended rule grounding, and substantiation-screening framing.
**Depends on**: Phase 33
**Requirements**: SAFE-01, SAFE-02, SAFE-03, SAFE-04
**Success Criteria** (what must be TRUE):

  1. Conformance tests prove no `pending`, unconfirmed, low-confidence, or stale value can produce a `SUBSTANTIATED` verdict.
  2. Privacy tests prove PII cannot reach stdout, the repo, the corpus, public reports, tracked fixtures, or non-vault output paths.
  3. Retrieve-what-you-cite tests prove every registry rule grounds the intended current rule rather than a historical, adjacent, or wrong-family chunk.
  4. Release docs and report wording frame the output as CRS substantiation screening and not legal advice.

**Plans**: 4 plans

Plans:

- [x] 34-01-PLAN.md — SAFE-01 no-false-green conformance: no pending/unconfirmed/low-confidence/stale value produces SUBSTANTIATED across all four modules × the full factor grid (Wave 1)
- [x] 34-02-PLAN.md — SAFE-02 privacy containment conformance: no PII/ev_ id reaches stdout/repo/corpus/public-report/tracked-fixtures; non-vault output refused (Wave 1)
- [x] 34-03-PLAN.md — SAFE-03 retrieve-what-you-cite conformance: every registry rule grounds the intended rule + wrong-family/historical/adjacent negative controls (Wave 1)
- [x] 34-04-PLAN.md — SAFE-04 screening framing (report wording + README + SCREENING.md) + single authoritative conformance entry point (`scripts/run_conformance.py`) (Wave 2)
