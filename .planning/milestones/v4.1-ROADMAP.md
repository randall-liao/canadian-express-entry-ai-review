## Active Milestone

**v4.1 — CRS Auditor Hardening & Remediation**

**Goal:** Close the v4.0 auditor's known fail-closed coverage and operational gaps, then turn every
actionable finding into a grounded private remediation checklist and an explicitly redacted
professional-review packet — without inventing a second, ungrounded trust path.

**Granularity:** fine
**Phase range:** 35–39 (continues after v4.0 Phase 34)
**Requirement coverage:** 21/21 v4.1 requirements mapped
**Core build order:** coverage completion → operational hardening → grounded remediation checklist →
redacted professional-review packet → SAFE conformance / release consolidation. Coverage completion
and operational hardening are two mostly-parallel early tracks; both must land before remediation,
which precedes the packet, with the release gate consolidated last. Critical path:
Phase 35/36 → 37 → 38 → 39.

**Locked constraints for every phase (frozen — carried forward from v4.0):**

- **Zero new runtime dependencies** — ship on the exact stack that shipped v4.0 (pure Python +
  corpus-grounded YAML over existing, tested primitives; no PDF engine, templating engine, CLI
  framework, encryption library, or PII/NER scrubber).

- **No second trust path** — remediation and the packet are pure projections of an already-grounded
  `PrivateAuditReport`; they consume citation ids the audit already gated and never re-ground,
  re-score, or synthesize volatile requirements.

- **Vault-only PII boundary** — all PII, evidence pointers, full checklists, and packets stay under
  the git-ignored candidate vault behind the publish-safe allow-list; stdout/`--json` stays PII-light.

- **Fail-closed everywhere** — missing/corrupt grounding prerequisites and low-quality/ambiguous
  extraction refuse cleanly and produce no artifact; a `SUBSTANTIATED`-but-unpriced card is surfaced
  as unresolved, never collapsed into "complete"; no fabricated point value fills a gap.

- **No legal advice** — output is CRS substantiation *screening* and evidence organization; every new
  artifact carries the `SCREENING_NOTICE`, with no approval, eligibility, or outcome prediction.

- **Frozen trust path preserved** — the `search` → `--cite` → grounding gate → JSON envelope pipeline,
  field-level confirmation, `evidence_id` (`ev_`) ↔ `citation_id` namespace separation, and SQLite
  FTS5 keyword retrieval (no vectors/embeddings/cloud) remain unchanged; Python stays Poetry-managed.

- **Autonomous execution** — planning and execution proceed without clarification questions; agents
  make reasonable scope/implementation decisions and record rationale in milestone artifacts.

## Phase Details

### Phase 35: Coverage Completion

**Goal**: Every supported CRS factor produces a complete, non-fabricated point result — grounding higher-CLB first-official-language points and adding a confirmed sibling-relationship evidence chain so supported factors can reach a complete, reachable verdict.
**Depends on**: Nothing within v4.1 (builds on the shipped v4.0 auditor; parallelizable with Phase 36)
**Requirements**: COV-01, COV-02, COV-03, COV-04
**Success Criteria** (what must be TRUE):

  1. A first-official-language result at any benchmark the supported test-conversion tables emit — including higher-CLB (e.g., CLB 10+) — returns complete grounded points, with no fabricated or silently missing point total.
  2. Any factor that is `SUBSTANTIATED` but still cannot be priced from grounded rows is shown as an explicit unresolved/unpriced item, never a complete-looking result.
  3. Applicant can import sibling relationship, status, age, and Canadian-residence proof into the vault, have it extracted as `pending`, and confirm, correct, or reject each field before it is used in an audit.
  4. `additional.sibling` returns `SUBSTANTIATED` only when the claimed-scoped, confirmed evidence chain satisfies the corpus-grounded sibling rule; missing, stale, ambiguous, or cross-factor evidence stays `GAP`/`AT-RISK`.

**Plans**: 4 plans (2 waves; two mostly-parallel tracks — higher-CLB point rows + unpriced surfacing, and sibling extraction field + reachable decider)

Plans:

- [x] 35-01-PLAN.md — Higher-CLB first-official-language point grounding (COV-01) [wave 1]
- [x] 35-02-PLAN.md — Unpriced-`SUBSTANTIATED` surfacing net (COV-02) [wave 1]
- [x] 35-03-PLAN.md — Sibling extraction vocabulary + claimed-scoped quarantine (COV-03) [wave 1]
- [x] 35-04-PLAN.md — Reachable fail-closed `decide_sibling` + real seam (COV-04) [wave 2, depends 35-01/35-03]

### Phase 36: Operational Hardening

**Goal**: The auditor fails closed and stays trustworthy when grounding prerequisites are missing or corrupt, ships an accurate pinned example, and cannot be greened by low-quality or ambiguous documents.
**Depends on**: Nothing within v4.1 (independent hardening track, parallelizable with Phase 35; produces the pinned dotted-id example fixture and clean-refusal path that Phases 37–38 rely on)
**Requirements**: HARD-01, HARD-02, HARD-03, HARD-04
**Success Criteria** (what must be TRUE):

  1. When the corpus index is missing, empty, unreadable, corrupt, or content-drifted, the applicant receives a stable, PII-free, actionable refusal envelope using the frozen contract vocabulary plus a specific reason code.
  2. A grounding-prerequisite refusal exits non-zero, recommends the existing index/doctor recovery command, and writes no audit, remediation, packet, or database artifact.
  3. The shipped synthetic profile example uses canonical dotted factor IDs, is pinned to the live factor grid, and produces applicable non-`N/A` verdicts through the real CLI path.
  4. Adversarial rotated, low-text, password-protected, and ambiguous-date fixtures remain quarantined and cannot green or contaminate another factor through the real import → extract → confirm → audit seam.

**Plans**: TBD (~4 plans; three seams — typed index-readable preflight/refusal, re-keyed + pinned example profile, strengthened extraction regressions)

### Phase 37: Grounded Remediation Checklist

**Goal**: The applicant can turn a completed audit into a private, corpus-cited fix checklist — exactly one actionable item per unresolved finding — reusing already-grounded verdicts with no second advice path.
**Depends on**: Phase 35 (a complete, priced audit report to project) and Phase 36 (dotted-id example fixture + clean refusal on the shared audit path)
**Requirements**: REM-01, REM-02, REM-03, REM-04
**Success Criteria** (what must be TRUE):

  1. Applicant can generate a private remediation checklist from a selected completed audit run, with exactly one actionable item for each `GAP`, `AT-RISK`, or unresolved/unpriced factor.
  2. Each remediation item identifies the factor, verdict/reason, score impact, the existing grounded citation and verbatim rule span, and a deterministic action template keyed by factor and reason.
  3. Remediation reuses already-grounded audit verdicts and citations without re-scoring, re-grounding, synthesizing volatile requirements, or creating a second advice/trust path — same vault in produces an identical checklist out.
  4. The full remediation checklist and evidence pointers stay vault-only while stdout exposes only a PII-light summary, and every rendered artifact includes the substantiation-screening notice.

**Plans**: TBD (~3 plans; two-tier remediation model + `crawler/remediation.py`, `vault remediate` verb + `output/remediation/` subtree, projection/determinism/volatile-rule conformance)

### Phase 38: Redacted Professional Review Packet

**Goal**: The applicant can preview and produce an opt-in, explicitly redacted lawyer/RCIC review packet from selected findings — staged only inside the vault, excluding raw documents by default.
**Depends on**: Phase 37 (reuses finding-selection and report-load; the packet is a curated, redacted export layer over the remediation checklist)
**Requirements**: PKT-01, PKT-02, PKT-03, PKT-04, PKT-05
**Success Criteria** (what must be TRUE):

  1. Applicant can select audit/remediation findings and preview a dry-run redaction manifest before creating a lawyer/RCIC review packet.
  2. The packet is built from a closed allowlist projection whose schema structurally cannot carry raw applicant values, absolute paths, or `ev_` evidence IDs unless a field is explicitly admitted by the packet contract.
  3. Raw, rendered, and OCR document content is excluded by default; any document inclusion requires an explicit per-document opt-in and remains staged inside the candidate vault.
  4. Packet creation records what was included, excluded, and redacted, writes only under the guarded vault packet subtree, refuses non-vault destinations/path escapes, and scans rendered bytes before write.
  5. The packet presents selected findings, score impact, and resolvable authoritative citations with prominent screening-not-legal-advice framing and no approval, eligibility, or outcome prediction.

**Plans**: TBD (~4 plans; allowlist redaction model + `RedactionManifest`, `crawler/review_packet.py` + `vault review-packet` verb + `output/review-packet/` subtree, render-then-scan double gate + `--dry-run` preview, publish-safe subtree registration)

### Phase 39: SAFE Conformance & Release Consolidation

**Goal**: A single release-gate run proves the complete v4.1 flow holds every frozen invariant — pricing completeness, clean refusals, remediation/packet privacy, grounding, and screening framing.
**Depends on**: Phases 35, 36, 37, 38 (consolidates every new v4.1 surface)
**Requirements**: SAFE-05, SAFE-06, SAFE-07, SAFE-08
**Success Criteria** (what must be TRUE):

  1. Conformance proves every supported language benchmark is priced or explicitly unresolved, and no sibling or adversarial extraction state can produce a false-green verdict.
  2. Privacy tests prove remediation and packet defaults leak no PII, raw document bytes, absolute paths, or `ev_` IDs; both new output subtrees remain unstageable and non-vault writes fail closed.
  3. Retrieve-what-you-cite, deterministic-output, and static volatile-rule tests prove every requirement-bearing remediation/packet line derives from an existing grounded rule rather than synthesized advice.
  4. The single release-gate command exercises coverage, refusal, remediation, packet, privacy, grounding, and screening-framing checks for the complete v4.1 flow.

**Plans**: TBD (~3 plans; coverage/no-false-green + priced-or-flagged assertions, remediation/packet privacy + non-vault-refusal + redaction-leak assertions, retrieve-what-you-cite/determinism/screening-framing + single release-gate entry point)
