### Phase Details

#### Phase 40: SAFE Freshness & Effective-Date Foundation

**Goal**: Land the shared freshness/effective-date/staleness guard and the snapshot-aware preflight
*before* the screens that depend on them, so no out-of-window or stale rule row or local snapshot can
ever contribute to a green verdict.
**Depends on**: Shipped v4.1 stack (Phase 39) — first v5.0 phase.
**Requirements**: SAFE-09, SAFE-10
**Success Criteria** (what must be TRUE):

  1. A shared freshness guard rejects any grounded rule row or local snapshot outside its effective window or beyond its staleness bound, so it cannot contribute to a green verdict (mirrors the shipped `within_validity`/`_in_window` semantics).
  2. The staleness bound is read from a grounded/config value — never an inlined literal — and a single promoted gate-subset helper is reused by every screen rather than re-implemented per screen.
  3. The corpus/index/snapshot preflight refuses cleanly — a stable PII-free reason code, non-zero exit, and zero audit/screen/database artifacts written — when a required snapshot or index is missing, empty, unreadable, corrupt, stale, or content-drifted.
  4. The same preflight passes against a healthy index/snapshot and permits downstream screens to proceed.

**Plans**: 3 plans (2 waves)
