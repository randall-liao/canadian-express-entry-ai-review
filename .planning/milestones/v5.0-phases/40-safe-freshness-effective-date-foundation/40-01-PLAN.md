<objective>
Ship the SAFE-09 freshness / effective-date MECHANISM as additive sibling helpers beside the
shipped `within_validity` / `_in_window` primitives, proven with out-of-window / stale / after-
reference negative controls. The staleness bound is read from a grounded `validity_window` row via
the shipped `_window_days` reader — never an inlined literal — and drift coverage over a freshness-
bound row shape is proven via `registry_fingerprint`.

This plan implements the "stale / superseded / out-of-window never greens" mechanism half of the
milestone's dominant safety invariant (SAFE-09, ROADMAP Phase 40 SC1 + SC2 bound clause). It exposes
`within_freshness` / `row_in_effect` as separately-callable, discoverable helpers for the later v5.0
screens (Phases 42/44/45 wire them; Phase 46 proves them centrally). It does NOT wire them into any
shipped decider (that would change the frozen CRS grid — out of scope).

**Honest grounding decision (Assumption A2 / Open Question 1 — deep-work rule 5):** the CONCRETE DLI
snapshot max-age value and its authoritative citation are a Phase 41 (STUDY-01) data responsibility,
grounded alongside the DLI corpus family. A probe of the current corpus (`corpus/index.db`) confirms
NO authoritative "list is updated every N days" / max-age span is groundable today. Therefore this
plan does NOT add a bound row to the shipped `crawler/data/crs_rules/*.yaml` registry (a non-gap row
would fail the whole-registry grounding conformance; a `gap:true` row would fail the shipped
`test_gap_rows_are_surfaced_by_coverage` because a non-required `safe.*` rule id is not surfaced by
`coverage_report`). Instead, SAFE-09's "grounded/config value, never inlined" and "drift-covered" are
proven with SYNTHETIC grounded `validity_window` fixtures (exactly how `_validity_registry()` proves
`within_validity`). The mechanism fails closed (no grounded window ⇒ False). `_FRESHNESS_FIELD` ships
the field-name contract (`snapshot_max_age`) Phase 41's real grounded row will populate. Record this
rationale in the SUMMARY.

Purpose: Deliver the discoverable fail-closed freshness API so no later screen has to hand-roll date
math, and prove it with the negative controls that catch the milestone's dominant false-green risk.
Output: `within_freshness`, `row_in_effect`, `_FRESHNESS_FIELD` in `crs_audit.py`; a new
`test_freshness_staleness.py`; an extended `test_crs_rules.py` fingerprint-drift test.
</objective>
