# Architecture Research

**Domain:** v4.0 CRS Profile ↔ Document Substantiation Auditor integration for the shipped `corpus-crawler` Python system  
**Researched:** 2026-07-05  
**Confidence:** HIGH for integration with shipped search / citation / gate / envelope primitives; MEDIUM for final extraction-library choices because extraction dependencies are implementation-specific.

## Standard Architecture

### System Overview

The v4.0 architecture should be an additive private-data layer and auditor pack around the frozen v3.0/v3.1 primitives. Do **not** rebuild retrieval, citation resolution, grounding, rendering, or the JSON envelope.

The public corpus remains the only source of immigration rules.

### Structure Rationale

- **Keep the vault under `personal/`, not a new top-level directory.** The repo already ignores and publish-guards `personal/`. Reusing it avoids a second privacy boundary and means existing `CORPORA_PREFIXES` logic already flags accidental tracked private files.
- **Centralize path resolution.** The current profile/output resolution is split between checklist code and CLI write gates. v4 should introduce one resolver and have all private writes use the same anchored containment check.
- **Use platformdirs only as a packaged-install fallback.** In a source checkout, default to the repo-local `personal/` so `.gitignore` and publish-safety gates protect the vault. If running as an installed package outside a repo, fall back to `platformdirs.user_data_dir(...)/personal`; `PR_PERSONAL_DIR` overrides both.
- **Store rule registry files publicly; store applicant evidence privately.** CRS rules are generic and citable, so they belong in the public harness. Candidate profile, documents, extraction artifacts, and audit evidence belong only in the vault.
- **Make Markdown agents thin.** The auditor specs should explain factor-specific behavior and call stable commands; deterministic joins, schema validation, and gating should live in tested Python modules.

## Candidate Vault Design

### Path Resolution Contract

Recommended private-root resolver:

```python
def personal_root(explicit: str | None = None) -> Path:
    if explicit:
        return Path(explicit).expanduser().resolve()
    if os.environ.get("PR_PERSONAL_DIR"):
        return Path(os.environ["PR_PERSONAL_DIR"]).expanduser().resolve()
    if running_from_repo_checkout():
        return (repo_root() / "personal").resolve()
    return (Path(platformdirs.user_data_dir("pr-review-agents")) / "personal").resolve()
```

Then:

```python
candidate_root = personal_root() / "candidates" / safe_candidate_id
vault_db = candidate_root / "vault.sqlite"
```

Rules:

1. Candidate IDs are safe slugs or generated IDs, never names/UCI/passport numbers.
2. Original filenames may contain PII; store them in SQLite, not in public output. On disk, copy raw files to content-addressed names.
3. Every write path must resolve under `personal_root()`. Reject symlink escapes and `..` escapes before writing.
4. `--json` stdout for vault/audit commands should contain only PII-light summaries. Detailed values and reports go to `candidate_root/output/` or tables in `vault.sqlite`.

### SQLite Schema Option

This schema mirrors the corpus DB pattern: stable logical IDs, content hashes, metadata tables, and derived artifacts linked back to source files. Use Pydantic models at command boundaries if available, but keep the persisted format plain SQLite + JSON text.

```sql
CREATE TABLE vault_meta (
    key TEXT PRIMARY KEY,
    value TEXT NOT NULL
);

CREATE TABLE candidates (
    candidate_id TEXT PRIMARY KEY,
    label TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE TABLE crs_profile_factors (
    factor_id TEXT PRIMARY KEY,
    factor_group TEXT NOT NULL,
    claimed_points INTEGER,
    claimed_level TEXT,
    claimed_value_json TEXT NOT NULL,
    source TEXT NOT NULL,              -- user_entry | profile_import | corrected
    confirmed_at TEXT,
    updated_at TEXT NOT NULL
);

CREATE TABLE documents (
    document_id TEXT PRIMARY KEY,
    candidate_id TEXT NOT NULL REFERENCES candidates(candidate_id),
    doc_type TEXT NOT NULL,            -- language_test | eca | employment_reference | nomination | ...
    file_sha256 TEXT NOT NULL,
    storage_relpath TEXT NOT NULL,     -- relative to candidate root
    original_name TEXT,                -- private; never echo in public docs
    mime_type TEXT,
    page_count INTEGER,
    added_at TEXT NOT NULL,
    status TEXT NOT NULL               -- added | extracted | confirmed | rejected
);

CREATE TABLE extraction_runs (
    extraction_run_id TEXT PRIMARY KEY,
    started_at TEXT NOT NULL,
    completed_at TEXT,
    extractor_version TEXT NOT NULL,
    engine_json TEXT NOT NULL,
    status TEXT NOT NULL,              -- running | complete | failed
    notes TEXT
);

CREATE TABLE document_pages (
    page_id TEXT PRIMARY KEY,
    document_id TEXT NOT NULL REFERENCES documents(document_id),
    page_number INTEGER NOT NULL,
    image_relpath TEXT,
    text_relpath TEXT,
    render_sha256 TEXT,
    ocr_sha256 TEXT,
    extraction_run_id TEXT REFERENCES extraction_runs(extraction_run_id)
);

CREATE TABLE extracted_values (
    value_id TEXT PRIMARY KEY,
    document_id TEXT NOT NULL REFERENCES documents(document_id),
    page_id TEXT REFERENCES document_pages(page_id),
    factor_id TEXT,                    -- nullable until linked
    field_name TEXT NOT NULL,          -- test_date | clb_reading | credential | noc | hours_per_week | ...
    raw_text TEXT,
    normalized_value_json TEXT NOT NULL,
    bbox_json TEXT,
    extractor_confidence REAL,
    extraction_run_id TEXT NOT NULL REFERENCES extraction_runs(extraction_run_id),
    confirmation_status TEXT NOT NULL, -- pending | confirmed | corrected | rejected
    confirmed_value_json TEXT,
    confirmed_at TEXT,
    confirmed_by TEXT
);

CREATE TABLE factor_evidence (
    factor_id TEXT NOT NULL REFERENCES crs_profile_factors(factor_id),
    value_id TEXT NOT NULL REFERENCES extracted_values(value_id),
    evidence_role TEXT NOT NULL,       -- primary | supporting | issuer | date | score | hours | noc
    PRIMARY KEY (factor_id, value_id, evidence_role)
);

CREATE TABLE audit_runs (
    audit_run_id TEXT PRIMARY KEY,
    candidate_id TEXT NOT NULL REFERENCES candidates(candidate_id),
    started_at TEXT NOT NULL,
    completed_at TEXT,
    rule_registry_version TEXT NOT NULL,
    corpus_db TEXT NOT NULL,
    grounding_verdict TEXT NOT NULL,   -- pass | fail
    overall_status TEXT NOT NULL       -- clear | needs_attention | blocked
);

CREATE TABLE audit_verdicts (
    audit_run_id TEXT NOT NULL REFERENCES audit_runs(audit_run_id),
    factor_id TEXT NOT NULL,
    factor_group TEXT NOT NULL,
    status TEXT NOT NULL,              -- SUBSTANTIATED | GAP | AT-RISK
    reason_code TEXT NOT NULL,
    rule_ids_json TEXT NOT NULL,

```

| Requirement | Design choice |

## Architectural Patterns

### Pattern 1: Candidate Vault as a Private Corpus-DB Mirror

**What:** Store applicant-specific documents and values in a local SQLite vault with stable IDs, content hashes, and derived artifacts, analogous to how the corpus index stores chunk metadata and citation IDs.

**When to use:** Always for profile, documents, extraction output, confirmations, and audit evidence. Do not use tracked YAML/JSON for real candidate data.

**Trade-offs:** SQLite is easy to inspect and test, but migrations must be explicit. Content-addressed files avoid filename leaks, but the UI must preserve original names inside the private DB for user recognition.

**Example invariant:**

```python
assert candidate_root.resolve() == personal_root() or personal_root() in candidate_root.resolve().parents
assert not document_id_contains_pii(document_id)
assert raw_file_path.is_relative_to(candidate_root)
```

### Pattern 2: Extraction Quarantine + Mandatory Confirmation Barrier

**What:** Extraction is allowed to be non-grounded, but its output is quarantined as `pending`. Auditors may read only `confirmed` or `corrected` values.

**When to use:** Every OCR/render/text extraction path. This is the only safe way to make automated reading compatible with the fail-closed ethos.

**Trade-offs:** Adds a user checkpoint, but prevents silent OCR errors from becoming false CRS confidence.

**State machine:**

```
raw document
   ↓ extract
pending extracted value
   ├── confirm   → confirmed value → eligible for audit
   ├── correct   → corrected value → eligible for audit, original retained
   └── reject    → rejected value  → never eligible
```

Auditor query rule:

```sql
SELECT *
FROM extracted_values
WHERE factor_id = ?
  AND confirmation_status IN ('confirmed', 'corrected');
```

If no confirmed evidence exists for a claimed factor, the auditor can emit a cited `GAP` only if the required rule itself is grounded. It must not infer values from pending extraction output.

### Pattern 3: Grounded CRS Rule Registry as a Precomputed Cited Table

**Recommendation:** Use a **precomputed, PII-free cited rule table generated and validated from per-factor query specs**, not ad hoc free-form search inside each audit run.

The registry should keep the v3.1 agent discipline: bake short high-signal queries and non-volatile selection rules, then validate the selected citation + quote against the real corpus. The difference is that v4 has many factors sharing rules, so the selected rule rows should be centralized and versioned.

```
query spec ──search──► selected hit ──search --cite──► verbatim chunk text
      │                                                   │
      └──────────────► rule row: rule_id, citation, quote, machine checks
                                                              │
                                                              ▼
                                             ground/eval validates every row
```

Suggested rule row:

```yaml
rule_id: core.language.first.approved_test
factor_group: core_human_capital
factor_ids: ["core.language.first"]
check_type: admissibility
query: "language test approved results"
selector:
  family: guidance
  require_title_contains: "language"
claim_text: "Official-language CRS evidence must use an approved language test result."
citations:
  - chunk_id: "guidance/language-test.md#004"
    quote: "<verbatim substring copied from the resolved chunk at build time>"
machine_check:
  kind: accepted_enum
  field: test_type
  accepted_values:
    - value: "IELTS General Training"
      citation_index: 0
    - value: "CELPIP-General"
      citation_index: 0
```

Rules:

1. **The corpus remains the source of truth.** The registry is a grounded cache/manifest, not a new authority.
2. **No auditor uses a rule row unless its citation resolves and its quote passes the gate.**
3. **No volatile threshold lives only in agent prose.** If a validity window, CLB threshold, duration, points table, issuer, accepted-test name, or document type is machine-readable, it must be paired with a rule citation and quote.
4. **Keep query specs.** Conformance should be able to re-run the query/selector and prove it still retrieves a chunk that grounds the row, just like the v3.1 document-agent conformance.
5. **Runtime auditors can use `--cite` over registry citations.** Ranked search happens during registry build/refresh/conformance; audit runs should prefer stable, already-validated rows to reduce agent drift.

### Pattern 4: Auditor as Deterministic Join of Confirmed Evidence + Grounded Rules

**What:** Each factor-group auditor reads a narrow vault slice and the relevant validated rule rows, then deterministically derives verdicts:

```
confirmed vault evidence + grounded rule row + deterministic comparator
        → SUBSTANTIATED / GAP / AT-RISK
```

**When to use:** All CRS factor checks: presence, value, and admissibility.

**Trade-offs:** This avoids semantic/NLI overreach but requires careful factor schemas and comparison functions. It also makes extraction errors visible because unconfirmed values simply cannot pass.

Verdict semantics:

| Verdict | Meaning | Required citation behavior |
|---------|---------|----------------------------|
| `SUBSTANTIATED` | Confirmed document evidence exists and deterministic checks meet the grounded rule. | Cite the admissibility/threshold rule rows used. |
| `GAP` | Required evidence is missing, unconfirmed, or incomplete. | Cite the rule that creates the evidence requirement; if no rule is grounded, abstain/block instead. |
| `AT-RISK` | Evidence exists but conflicts with the claimed level, value window, issuer, format, or threshold. | Cite the rule/threshold that the confirmed value appears not to meet. |

Keep the PII split:

- Rule/admissibility/threshold text goes in `claims[]` with citation + quote.
- Candidate values, document IDs, page numbers, and extraction notes go in `basis[]` or the private audit JSON.
- Rendered public-style claim text should use vault IDs, not names or original filenames.

### Pattern 5: Existing Envelope and Gate for Auditor Output

**Recommendation:** Yes, the auditor should emit through the existing JSON envelope contract.

Add a command value such as `crs-audit` or `audit-crs`, but keep the five-key envelope unchanged:

```json
{
  "schema_version": "1.0",
  "ok": true,
  "command": "crs-audit",
  "result": {
    "grounding": {
      "verdict": "pass",
      "total_claims": 18,
      "grounded": 18,
      "ungrounded": 0,
      "violations": []
    },
    "overall_status": "needs_attention",
    "summary": {
      "SUBSTANTIATED": 9,
      "GAP": 2,
      "AT-RISK": 1
    },
    "out": "personal/candidates/default/output/crs-audit/<run-id>.md",
    "audit_run_id": "<run-id>"
  },
  "error": null
}
```

Contract guidance:

- `ok:false` remains only for execution errors: invalid vault path, missing DB, malformed registry, missing dependency.
- `grounding.verdict:"fail"` is a fail-closed grounding failure: write nothing; report violations; do not emit partial verdicts.
- `overall_status:"needs_attention"` is a valid grounded audit result, not an execution error. It should still write the report because GAP/AT-RISK findings are the product.
- Keep stdout PII-light. The detailed PII-bearing report and JSON belong under the candidate's private `output/` directory.

## Data Flow

### End-to-End Request Flow

```
[Applicant CRS profile + document files]
        │
        ▼
[vault import]
        │  writes profile factors + content-addressed raw files
        ▼
[candidate vault: vault.sqlite + files/raw]
        │
        ├──────────────► [extraction]
        │                    │ render pages + extract text/OCR
        │                    ▼
        │              [pending extracted_values]
        │                    │
        │                    ▼
        │              [confirm what I read]
        │                    │ user confirms/corrects/rejects
        │                    ▼
        │              [confirmed evidence]
        │
        ├──────────────► [CRS rule registry validation]
        │                    │ search/query specs + --cite + ground
        │                    ▼
        │              [validated rule rows]
        │
        ▼
[factor-group auditor agents]
        │ read confirmed evidence + validated rules
        │ perform presence/value/admissibility checks
        ▼
[structured answer object]
        │ claims[] = cited rule/verdict claims
        │ basis[]  = private evidence pointers and confirmed values
        ▼
corpus-crawler --json ground / in-process grounding.check_answer
        │
        ├── fail: any uncited/unresolvable/quote mismatch → write nothing
        │
        └── pass: render → publish-safety scan → write under private output/
```

### Key Data Flows

1. **Vault import flow:** profile factor breakdown and raw documents enter `personal/candidates/<id>/`; original filenames and document contents never enter the repo, corpus DB, rule registry, or tracked tests.
2. **Extraction flow:** render-to-image + text extraction writes `pending` values with page/bbox/source metadata. This is the one automated non-grounded interpretation step.
3. **Confirmation flow:** the user reviews exactly what extraction read. Only `confirmed` or `corrected` values can satisfy evidence checks.
4. **Rule registry flow:** per-factor query specs search the corpus; selected chunks are resolved with `--cite`; verbatim quotes are stored in public rule rows; the registry is validated through the same grounding gate.
5. **Audit flow:** each factor-group auditor reads only its factor slice, links confirmed evidence to rule rows, emits verdict claims, and refuses output if any rule citation/quote fails the gate.
6. **Output flow:** machine envelope on stdout is PII-light; full reports go only under the private candidate output directory.

### State Management

```
document.status:
  added → extracted → confirmed
             │
             └── rejected

extracted_values.confirmation_status:
  pending → confirmed
          → corrected
          → rejected

audit_runs.overall_status:
  blocked          # missing/failed registry, no grounded output
  clear            # all audited factors SUBSTANTIATED
  needs_attention  # at least one GAP or AT-RISK, but output is grounded
```

### How Extraction Remains the Sole Non-Grounded Step

Strict boundary:

| Layer | Grounded? | Why |
-------|-----------|-----|
| User CRS profile input | Not corpus-grounded | It is applicant-provided evidence/claim input, not an immigration-rule assertion. |
| Automated extraction | Not corpus-grounded | It reads private documents; must be quarantined and confirmed. |
| Confirmation | Human-confirmed | The user verifies/corrects extracted evidence before audit use. |
| Admissibility rules | Grounded | Must cite IRCC/IRPR/PDI corpus chunks and pass quote-substring gate. |
| Threshold/value-window rules | Grounded | Machine-readable thresholds must be paired with cited quotes and registry validation. |
| Presence/value/admissibility verdicts | Grounded-by-rule + deterministic | Verdicts may use confirmed evidence, but every rule or threshold they depend on must pass the existing gate. |

The auditor must refuse to create a factor verdict when:

- the factor has only pending extraction values;
- the required CRS rule row is missing;
- the rule row's citation is unresolvable;
- the row's quote no longer appears verbatim in the resolved chunk;
- the comparator needs a threshold that is not represented in a grounded rule row.

## Scaling Considerations

This remains a local single-applicant system. The scaling axes are document volume, extraction cost, factor coverage, and corpus/rule drift.

| Scale | Architecture Adjustments |
|-------|--------------------------|
| One applicant, tens of documents | SQLite + local files is enough. Cache rendered pages by document hash. |
| Multiple candidate profiles on one machine | Namespace by `personal/candidates/<candidate-id>/`; one vault DB per candidate keeps backups and deletion simple. |
| More immigration programs later | Add program namespace to factor IDs and rule registry files; do not mix PNP/family/study rules into Express Entry CRS rows. |
| Larger document sets | Add optional FTS table over private extracted text inside the vault, but never merge it with the public corpus index. |

### Scaling Priorities

1. **First bottleneck: extraction runtime.** Fix with content-hash caching of rendered pages/text before adding services.
2. **Second bottleneck: rule coverage drift.** Fix with registry validation/conformance and explicit "blocked" results for stale citations.
3. **Third bottleneck: factor combinatorics.** Fix with stable factor IDs and shared rule rows; do not duplicate the same threshold across agents.

## Anti-Patterns

### Anti-Pattern 1: A Second Trust Path for CRS Rules

**What people do:** Implement a separate CRS citation resolver or custom "rule proof" validator.

**Why it's wrong:** It bypasses the shipped search/`--cite`/ground contract and creates two definitions of grounded.

**Do this instead:** Registry rows and auditor claims must pass through existing `searchindex.resolve` / `grounding.check_answer` / `corpus-crawler --json ground`.

### Anti-Pattern 2: Letting Pending Extraction Drive Verdicts

**What people do:** OCR a language test or ECA and immediately mark a factor substantiated.

**Why it's wrong:** Extraction is the one non-grounded step and can silently misread charts, dates, tables, or names.

**Do this instead:** Store extraction output as `pending`; require user confirmation/correction; auditors read confirmed values only.

### Anti-Pattern 3: Hard-Coding CRS Thresholds in Agent Prose

**What people do:** Put CLB levels, validity windows, work-duration thresholds, or points-grid numbers directly in Markdown agent files.

**Why it's wrong:** These are volatile rule facts. Hard-coded values rot and bypass citations.

**Do this instead:** Store machine-readable thresholds in the CRS rule registry, each paired with a citation ID and verbatim quote that passes the gate.

### Anti-Pattern 4: Putting Real Vault Fixtures in the Repo

**What people do:** Commit a sample `vault.sqlite`, extracted document text, or OCR page image for tests.

**Why it's wrong:** The vault is PII by design; even "sample" documents tend to leak names, IDs, or paths.

**Do this instead:** Use `personal.example/` with synthetic YAML only, plus in-memory/tempdir synthetic SQLite fixtures in tests.

### Anti-Pattern 5: Emitting PII-Rich Audit JSON to Stdout by Default

**What people do:** Return full extracted values and document names in the `--json` envelope.

**Why it's wrong:** stdout is machine-readable but not confined to `personal/` and not publish-safety-scanned.

**Do this instead:** Envelope result contains counts, statuses, private output path, and run ID. Detailed evidence lives in the private output file or vault tables.

### Anti-Pattern 6: Treating the Grounding Gate as Semantic Entailment

**What people do:** Assume a quote-substring pass proves the verdict is logically correct.

**Why it's wrong:** The shipped gate guarantees citation resolvability and quote presence, not semantic entailment.

**Do this instead:** Keep deterministic comparators small, show quotes beside claims, test representative factor cases, and abstain/block when a rule quote is ambiguous.

### Anti-Pattern 7: Merging Private Document Text into the Corpus Index

**What people do:** Add extracted applicant documents to `corpus/index.db` to search them with the same FTS tooling.

**Why it's wrong:** The corpus is authoritative public law/guidance. Mixing PII into it destroys the trust and privacy boundary.

**Do this instead:** If private text search is needed, add a separate vault-local FTS table inside `vault.sqlite`; never share tables or citation IDs with the public corpus.

## Integration Points

### External Services

| Service | Integration Pattern | Notes |
|---------|---------------------|-------|
| Cloud OCR / document AI | Do not use by default | Would export PII outside the local machine and violate the local-only privacy model unless a future explicit opt-in design is researched. |
| Local render/OCR tools | Optional extraction extra | Keep extraction dependencies optional and local. The architecture only requires render-to-image + text output and confirmation, not a specific library. |
| Authoritative rule sources | Existing corpus only | CRS rules come from the already-crawled IRCC/IRPR/PDI corpus via search/`--cite`, not live web calls during audit. |

## Suggested Build Order

The seed order (`vault → extraction → rule registry → auditor pack`) is close, but the rule registry does **not** depend on extraction and should be pulled earlier to de-risk the grounded rule surface.

Recommended order:

| Phase | Build | Dependencies | Why |
|-------|-------|--------------|-----|
| 1 | **Path resolver + candidate vault foundation** | Existing `personal/` boundary, SQLite pattern | Must exist before any real documents/profile data are introduced. Establishes PII containment and factor IDs. |
| 2 | **Grounded CRS rule registry** | Corpus index/search/gate; factor ID schema from Phase 1 | Public and PII-free. Unlocks coverage audits and prevents hard-coded thresholds before auditors are written. |
| 3 | **Extraction + confirmation checkpoint** | Vault document/value schema from Phase 1; expected fields from Phase 2 | Isolates the one non-grounded step and proves pending values cannot drive verdicts. |
| 4 | **One auditor vertical slice** | Vault confirmed evidence + validated rules | Start with a high-value slice such as language or education to prove SUBSTANTIATED/GAP/AT-RISK and envelope output end to end. |
| 5 | **Full modular auditor pack** | Proven slice + registry coverage | Fan out to core human capital, spouse/common-law, skill transferability, and additional points. |
| 6 | **Conformance and safety hardening** | All components | Real-corpus local conformance, synthetic CI tests, no-PII stdout checks, pending-value refusal tests, stale-citation failure tests. |

If the roadmap needs more parallelism: after Phase 1, Phase 2 (rule registry) and Phase 3 (extraction) can proceed in parallel. The auditor pack should wait until both the registry and confirmed-evidence path are proven.
